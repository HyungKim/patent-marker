# 성능 측정 — 개선 폭을 숫자로 보이기 (회사 보고용)

[검토 반영] 으로 쌓인 **사람이 확정한 정답**을 문제지 삼아, 도구가 얼마나 잘 잡는지를
숫자로 잽니다. 회차마다 이력이 쌓여서 "최초 대비 얼마나 좋아졌는지" 를 누적으로 보여 줍니다.

> 웹 화면 **[성능 기록]** 탭 → **[성능 측정 실행]** 버튼 하나면 됩니다.
> 문단 묶음마다 모델을 두 번 부르므로 몇 분 걸립니다. 결과와 이력은
> `review_data/eval_history.jsonl` 에만 저장되며 외부로 나가지 않습니다.

---

## 1. 어떻게 재나 — "같은 문제지로 두 번 채점"

측정을 실행하면 같은 문제지(확정 정답 모음)로 두 가지 설정을 **동시에** 채점합니다.

| | 최초 설정 (기준점) | 현재 설정 |
|---|---|---|
| 규칙 사전 | 기본 사전만 | 기본 사전 + [사전에 추가] 한 표현 |
| 판정 프롬프트 | 기본 지시서만 | 기본 지시서 + 사내 검토 확정 사례 주입 |
| 모델 | qwen3:8b (출하 기본) | 지금 쓰는 모델 |

이렇게 하면 "도구를 처음 설치했을 때" 와 "검토를 반영해 온 지금" 의 차이가
**같은 시험 문제에 대한 점수 차이**로 나오기 때문에, 개선 폭을 공정하게 주장할 수 있습니다.

**문제지는 어디서 오나** — [검토 반영] 탭에서 [반영 저장] 할 때마다
사람이 최종 확정한 구간(맞은 것·놓친 것·지운 오탐)이 `review_data/dataset.jsonl` 에 쌓이고,
측정은 이것을 그대로 채점 기준으로 씁니다. 즉 **검토를 많이 할수록 문제지가 커지고 측정이 정확해집니다.**

## 2. 지표 읽는 법 (쉬운 말로)

| 지표 | 뜻 | 높으면 |
|---|---|---|
| **재현율** | 잡아야 할 정답 중 실제로 잡은 비율 | 누락이 없다 |
| **정밀도** | 도구가 잡은 것 중 진짜였던 비율 | 헛짚지 않는다 |
| **F1** | 위 둘의 조화 평균 (종합 점수 하나가 필요할 때) | 균형이 좋다 |
| **등급 일치율** | 맞게 잡은 것 중 등급(A/B/C)까지 맞힌 비율 | 등급 판정도 정확하다 |

숫자 옆의 **Δ(델타)** 는 "최초 설정 대비 현재 설정이 몇 %p 좋은가" 입니다. 이것이 개선 폭입니다.

숫자 밑에는 **항목 단위 개선**도 함께 나옵니다 — 보고서에 그대로 쓰기 좋은 부분입니다.
- "최초가 놓친 정답 N건을 현재는 잡음" (새로 잡게 된 문장 예시 포함)
- "최초의 오탐 N건이 사라짐"
- "퇴행 N건" — 최초는 잡았는데 현재가 놓친 것. **0이 아니면 원인을 확인하세요**
  (보통 [사전에 추가] 문구나 주입 예시가 다른 문장을 밀어낸 경우).

## 3. 누적 이력 — "언제 무엇을 바꿨더니 얼마나 좋아졌나"

측정할 때마다 한 회차가 이력 표에 쌓입니다. 각 회차에는
- 그 시점의 문제지 크기 (정답 구간 수)
- **직전 회차 이후 바뀐 것** — 추가한 사전 표현(이름까지), 쌓인 예시 증가량, 교정 데이터 증가량, 모델 변경
  · 프롬프트 **주입 칸 수**를 바꿨다면 별도로 굵게 표시됩니다. 이때는 점수 변화가
    '교정이 좋아져서' 가 아니라 '예시를 더 넣어서' 일 수 있으므로 **그 회차를 경계로**
    **앞뒤를 직접 비교하지 마세요.** (쌓인 예시가 느는 것은 프롬프트와 무관합니다)
  · 도구를 새 버전으로 바꾼 직후 첫 회차는 `기록 없음 → 10` 처럼 표시됩니다.
    직전 회차가 이 값을 남기지 않았다는 뜻이고, 그 회차야말로 프롬프트가 가장 크게
    바뀐 지점이므로 역시 앞뒤를 직접 비교하지 마세요.
    (화살표 오른쪽 숫자는 최대 12 입니다. 예전 버전은 예시를 12건까지만 보관했어서
     업데이트 직후에는 정답 칸이 덜 채워져 10 으로 나올 수 있습니다 —
     예시가 사라진 것이 아니라 아직 덜 쌓인 것이고, [반영 저장] 을 더 하면 12 로 찹니다.
     이 PC 에서 성능 측정을 한 번도 한 적이 없으면 비교 대상이 없어 이 줄 자체가
     안 뜨고 "첫 측정 (기준점)" 만 표시되는데, 그것도 정상입니다.)
- 최초→현재 점수와 Δ

가 함께 기록되므로, "9/12에 사전 3개를 추가했더니 재현율이 +11%p" 같은
**개선 이야기의 근거**가 자동으로 만들어집니다.

측정 회차 표 위에는 **개선 타임라인**이 함께 표시됩니다 — 검토완료본을 반영한 것,
[사전에 추가] 로 표현을 등록한 것, 성능을 측정한 것이 **시간순으로 한 줄씩** 이어져서
"이걸 바꿨더니 → 이렇게 좋아졌다" 는 흐름을 그대로 읽을 수 있습니다
(원본: `review_data/change_log.jsonl`).

**[보고용 표 복사]** 버튼은 측정 표와 개선 타임라인을 함께 마크다운으로 복사해 줍니다.
메일·위키·보고서에 붙여 넣으면 됩니다.

## 4. 보고서에 쓸 때 권장 문장 (예시)

> 사내 검토로 확정된 정답 N구간을 문제지로, 도입 초기 설정과 현재 설정을 동일 조건에서 채점한 결과
> 재현율 xx% → xx% (+xx%p), 정밀도 xx% → xx% (+xx%p)로 개선됨.
> 개선은 GPU·추가 비용 없이 검토 결과 반영(사전 N건 추가, 확정 사례 프롬프트 주입)만으로 달성.

## 5. 알아 두면 좋은 것

- **회차끼리 절대값 비교는 조심** — 문제지가 회차마다 자라므로, 3회차 90%와 1회차 85%를
  직접 비교하기보다 **같은 회차 안의 "최초→현재" Δ** 를 개선 폭으로 읽는 것이 정확합니다.
  (같은 회차의 두 설정은 항상 같은 문제지로 채점되므로 공정한 비교입니다.)
- **측정 조건은 고정** — 추론 모드 꺼짐, 온도 등은 실제 분석 기본값과 같게 고정되어
  회차 간 조건 차이가 없습니다. 최초 설정용 qwen3:8b 가 PC 에 없으면 현재 모델로 대신
  채점하고 그 사실을 이력에 남깁니다.
- **문제지가 작을 때(정답 수십 구간 미만)** 는 숫자가 한두 건에 크게 흔들립니다.
  회사 보고에는 정답 30구간 이상 쌓인 뒤의 수치를 권합니다.
- **처음부터 다시** — `review_data/eval_history.jsonl` 을 지우면 이력이 초기화됩니다
  (문제지·검토 데이터는 그대로).
- **점검** — `python tests/test_eval.py` 가 채점 수학 전체를 모델 없이 몇 초 만에 검사합니다.

## 속도는 따로 잽니다 — `review_data/run_log.tsv`

이 문서의 지표는 **정확도**입니다. **속도**(토큰 수·초당 토큰·총 소요)는 분석이 끝날 때마다
`review_data/run_log.tsv` 에 한 줄씩 자동으로 쌓이고(엑셀로 열림), 화면 집계 카드 아래에도 같은 내용이 뜹니다.
프로그램 자체의 개선 이력(방법·부분·이유·정량 결과)과 읽는 법은 [05_개선_이력.md](05_개선_이력.md).
