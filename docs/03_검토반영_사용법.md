# 검토 반영 — 검토완료본으로 판정을 좋게 만들기

마킹 결과를 사람이 교정한 파일(**검토완료본**)을 넣으면, 도구가 "어디를 틀렸는지" 를 스스로 학습 재료로 쌓고
다음 분석부터 자동으로 반영합니다. 모델 훈련(GPU)이 없어도 되는, 이 도구의 기본 개선 경로입니다.

> 모든 데이터는 `review_data/` 폴더(이 PC 안)에만 저장됩니다. 외부로 나가지 않습니다.

---

## 1. 검토하는 방법 (PowerPoint 에서)

분석이 끝나 `output` 폴더에 저장된 **마킹된 PPTX** 를 PowerPoint 로 열고, 형광펜만 고칩니다. 글자는 고치지 마세요.

| 하고 싶은 것 | 이렇게 |
|---|---|
| 잘못 잡았다 (오탐) | 그 구간을 선택 → 형광펜 **색 없음** 으로 지우기 |
| 놓쳤다 (누락) | 그 구간을 선택 → 형광펜 칠하기 |
| 등급이 틀렸다 | 형광펜 **색을 바꾸기** |
| 맞게 잡았다 | 그대로 두기 |

도구가 넣은 첫 슬라이드의 범례 상자는 그대로 두면 됩니다(비교할 때 자동으로 뺍니다).
"문구도 표시" 옵션을 켜서 만든 파일이라면 형광펜 뒤의 【출원검토필요】 문구도 지우든 놔두든 상관없습니다 —
같은 PC 에서 분석한 기록과 비교할 때는 문구를 아예 보지 않고, 기록이 없는 축소 모드에서는 형광펜만 지워진 자리의
문구가 "사람이 지웠다" 는 단서로 쓰이므로 오히려 남겨 두는 편이 낫습니다.

**색 규약** — 정확한 색이 아니어도 됩니다. 비슷한 계열이면 자동으로 알아봅니다.

| 색 계열 | 뜻 |
|---|---|
| 노랑 (기본 형광펜 노랑 포함) | **A** — 구체적 기술 수단이 드러남 |
| 하늘 / 파랑 / 청록 | **B** — 수단은 없지만 존재가 시사됨 (묵시) |
| 살구 / 빨강 / 분홍 | **C** — 공개 관련정보 (공개전 출원완료 필요) |

검토가 끝나면 **저장**합니다 (파일명은 자유. 예: `보고서명_검토완료.pptx`).

## 2. 넣는 방법 (웹 화면에서)

1. `run.bat` 으로 화면을 열고 위쪽 **[검토 반영]** 탭을 누릅니다.
2. 검토완료 PPTX 를 넣습니다. **여러 개를 한꺼번에** 넣어도 됩니다
   (몇 주치 검토본을 모아서 한 번에 반영할 때 편리합니다). 방법은 넷 중 편한 것으로:
   - **① input · output 폴더에서 고르기** — 검토완료본을 `C:\patent_marker\input` 에 복사해 두면
     목록에 나타납니다(결과 파일을 그 자리에서 고쳐 저장했다면 `output` 폴더 목록에 그대로 있습니다).
     여러 개를 클릭해 고른 뒤 **[선택한 파일 읽기]**.
   - **② 경로 붙여넣기** — 탐색기에서 Shift + 우클릭 → "경로로 복사" 한 것을 한 줄에 하나씩 붙여넣고 **[이 파일들 읽기]**.
   - **③ [찾기…]** — 프로그램이 직접 여는 파일 창. Ctrl 로 여러 개 선택.
   - **④ 브라우저로 올리기** — 끌어다 놓거나 클릭. 회사 PC 처럼 업로드가 막혀 있으면 ①~③ 을 쓰세요.
3. 파일별 교정 내역이 자동으로 계산되어 나옵니다.
   - **누락** — 사람이 새로 칠함 (모델이 놓친 것)
   - **오탐 제거** — 사람이 지움 (모델이 잘못 잡은 것)
   - **등급 변경** — 색을 바꾼 것
   - **일치** — 그대로 둔 것 (일치율 % 도 함께 표시)
4. 누락 중 **"사전 미포착"** 표시가 붙은 항목은 규칙 사전에도 없는 표현입니다.
   입력란의 핵심 표현을 다듬은 뒤 **[사전에 추가]** 를 누르면, 다음 분석부터 그 표현이 든 문단은
   모델이 놓쳐도 **반드시** 후보로 잡힙니다 (안전망 가중치로 등록).
5. **[반영 저장]** 을 누르면 넣은 파일 전부가 한 번에 저장됩니다. 이후 벌어지는 일:
   - 교정 기록이 `review_data/dataset.jsonl` 에 쌓임 (나중에 미세조정 재료)
   - 오탐·누락 사례가 판정 프롬프트의 **"사내 검토 확정 사례"** 로 자동 주입됨
     (오탐 반례 4개 + 정답 예시 8개). 교정은 **버리지 않고 계속 쌓이고**,
     그중 다음 기준으로 고른 것만 프롬프트에 들어갑니다 —
     ① 최근 것 먼저 ② 단서 종류(카테고리)가 겹치지 않게 ③ 한 번의 반영이 독점하지 못하게
     (파일을 여러 개 올려도 **[반영 저장] 한 번은 한 번**으로 셉니다) ④ 모델이 실제로 놓친
     것을 '축소 모드 확정 라벨' 보다 먼저.
     그래서 보관이 수백 건이 되어도 **분석 속도와 메모리 사용은 그대로**입니다.
     ②에서 **"사전 미포착"**(규칙 사전에 아예 없던 새 표현)은 종류가 정해지지 않은 것이라
     서로 다른 것으로 봅니다 — 도구가 가장 배워야 할 재료라 한 칸에 뭉치지 않습니다.

     반례(4)와 정답(8)에 칸을 다르게 주는 이유 — 오탐은 매출·이익률 같은 경영지표에
     몰려서 4칸이면 대개 포화이고, 누락은 구성·제어·공정 등 넓게 퍼져서 8칸까지
     새로운 종류가 붙기 때문입니다. 칸을 더 늘려도 같은 종류가 반복될 뿐입니다.
   - 저장 직후 **"이번 반영으로 바뀐 것"** 리포트가 떠서, 교정 기록이 몇 건에서 몇 건이
     됐는지 · 프롬프트에 어떤 예시가 새로 주입되고 어떤 것이 밀려났는지 · 사전 표현
     개수가 어떻게 됐는지 보여 줍니다. 같은 내용이 **변경 일지**(`change_log.jsonl`)에
     계속 쌓여 [성능 기록] 탭의 **개선 타임라인**에서 측정 결과와 함께 볼 수 있습니다.

## 3. 알아 두면 좋은 것

- **분석 기록과의 짝 맞추기** — 분석할 때마다 판정 기록이 `review_data/analyses/` 에 자동 저장되고,
  검토본을 넣으면 글자 내용(지문)으로 그 기록을 찾아 비교합니다. 그래서 **분석한 PC 와 같은 PC 에서**
  검토 반영을 하는 것이 가장 정확합니다.
- **여러 개를 올릴 때** — 파일마다 따로 대조하므로 서로 다른 보고서를 섞어 올려도 됩니다.
  깨진 파일이 섞여 있으면 그 파일만 빠지고 나머지는 정상 처리됩니다.
  **같은 문서의 검토본 두 벌**을 함께 넣으면 첫 번째 것만 반영됩니다(교정이 서로 다를 수
  있어 한 번에 한 벌만) — 화면에 표시되며, 두 번째 벌은 저장 후 따로 넣으면 됩니다.
  형광펜이 하나도 없는 파일은 "검토본이 맞는지 확인하세요" 표시와 함께 제외됩니다.
- **기록이 없으면?** (다른 PC 에서 분석했거나 기록을 지운 경우) — "축소 모드" 로 동작합니다.
  형광펜 구간은 전부 '확정 라벨' 로 수집됩니다. ("문구도 표시" 로 만든 파일이면 형광펜 없이
  【출원검토필요】 문구만 남은 자리가 '오탐 추정' 으로 함께 수집됩니다.) 반영 효과는 거의 같지만,
  오탐(지운 것)까지 정확히 배우려면 분석한 PC 에서 반영하는 것이 좋습니다.
- **판정 기준 메모를 함께 쓰세요** — "매출 수치는 제외, 단 원가절감의 '수단'이 붙으면 포함" 처럼
  판단 기준을 한 장으로 적어 두면, 몇 달에 걸쳐 쌓이는 교정이 일관돼 데이터 가치가 높아집니다.
- **점검** — `python tests/test_review.py` 가 이 경로 전체를 모델 없이 몇 초 만에 검사합니다.

## 3-1. 검토가 쌓일수록 계속 나아지는 세 장치 — "검토 학습" (2026-09-22)

[반영 저장] 한 교정 내역은 다음 분석부터 세 가지 방식으로 되살아납니다. 모델(qwen3)을 학습시키는 것이
아니라 **모델 주변에 기억을 쌓는** 방식이라 GPU 없이 CPU 로 돌고, 데이터 양에 비례해 좋아집니다.
"완전히 똑같은 표현" 만이 아니라 **숫자·어순이 바뀐 표현, 같은 유형의 새 문장**까지 잡도록 만들었습니다.

| 장치 | 무엇을 하나 | 어디까지 '비슷하면' 잡나 | 결과 화면 표시 |
|---|---|---|---|
| ① 문단 기억 | 검토한 문단이 다시 나오면 모델에게 묻지 않고 **사람의 최종 판정**(형광펜 위치·등급)을 그대로 적용 | 문단의 90% 이상이 같으면 (숫자·날짜·몇 단어가 바뀐 재사용 장표) | 항목에 **검토 기억** 이름표 |
| ② 제외 사전 · 자동 규칙 | 검토에서 **지운** 표현을 모델이 또 잡으면 뺌 / 검토에서 **추가한** 표현은 규칙 사전에 자동 등록 | 숫자·공백이 달라도, 핵심어 2개 이상이 같은 문장에 있으면 (어순 무관) | 규칙 사전 이름표 · "제외 N" |
| ③ 유사 사례 검색 | 지금 분석하는 슬라이드와 **비슷한 확정 사례** 8+4개를 골라 모델 지시서에 붙임 (예전엔 전체에서 12개 고정) | 글자 겹침(기본) 또는 **뜻 기준**(bge-m3 임베딩, 설치 시) | 결과 아래 "사례 N(뜻 기준/글자 겹침)" |

### 켜고 끄기
- [문서 분석] 옵션 줄의 **"검토 학습 적용"** 체크박스 — 끄면 세 장치가 모두 멈추고 예전처럼 동작합니다.
  옆에 지금 쌓인 크기가 보입니다: `기억 문단 N · 자동 규칙 N · 제외 N · 사례 N`.
- **"뜻 기준 검색 (bge-m3)"** 체크박스 — 유사 사례를 글자 겹침이 아니라 뜻으로 찾습니다.
  `설치됨` 이면 켤 수 있고, `미설치` 면 회색으로 잠기며 글자 겹침으로 동작합니다. 설치는 검은 창에서
  `ollama pull bge-m3` (약 1.2GB, setup.bat 도 [5/5-3] 에서 받으려 시도). 없어도 ①②는 그대로 됩니다.
- 명령행: `python -m app.cli 파일 --no-learn` / `--no-embed`. 환경 변수 `PM_LEARN=0` 은 전체 기본값을 끕니다.
- 무엇이 적용됐는지는 결과 화면의 **"검토 학습: 기억 3문단(+5/−4) · 제외 1 · 사례 12(뜻 기준)"** 줄과
  `review_data/run_log.tsv` 의 "학습" 열에 남습니다.

### bge-m3 란
문장을 1,024개 숫자(좌표)로 바꾸는 **임베딩 모델**입니다. 뜻이 비슷한 문장일수록 좌표가 가까워서
"원가 절감" 과 "제조 비용 저감" 처럼 단어가 다른 문장도 찾습니다. 판단은 하지 않고 좌표만 만들기 때문에
빠릅니다(CPU 에서 문단 100개에 10~30초, 한 번 구한 좌표는 `review_data/embed_cache.json` 에 저장).
메모리 약 1.2GB 를 더 씁니다 — PC 가 버거우면 체크박스를 끄면 됩니다.

### 알아 둘 것
- **정직한 채점** — [성능 기록] 은 채점하는 바로 그 문단에서 나온 기억·규칙·사례를 **빼고**(leave-one-out) 돌립니다.
  그래서 "외워서 맞힌 점수" 가 아니라 "비슷한 문단으로 옮겨 가는 힘" 이 Δ 로 잡힙니다.
- **검토는 최종 상태가 기준** — 문단 기억은 검토완료본의 형광펜 상태를 "그 문단의 정답" 으로 봅니다.
  같은 문단을 나중에 다르게 검토하면 나중 것이 이깁니다.
- **한계** — 처음 보는 표현을 문맥으로 알아채는 힘은 모델(qwen3:8b) 몫이라 그대로입니다. 세 장치는
  회사 문서에서 **반복되는 것**(같은 장표의 다음 버전, 같은 팀의 어휘)을 확실히 잡는 데 가장 강합니다.
- 효과 측정과 수치는 `docs/05_개선_이력.md` 17회차.

## 4. 쌓인 데이터는 어디에

```
review_data/
├── analyses/          분석 기록 (지문.json) — 검토본과 비교할 기준
├── dataset.jsonl      교정 내역 원본 (한 줄 = 한 건)
├── examples.json      모범답안·반례가 계속 쌓이는 풀 (이 중 잘 고른 것만 프롬프트로)
├── extra_rules.json   [사전에 추가] 로 등록한 표현
├── embed_cache.json   뜻 기준 검색(bge-m3)이 구한 문장 좌표 (없으면 다시 계산, 지워도 됨)
├── change_log.jsonl   변경 일지 — 반영·사전 추가 때마다 무엇이 바뀌었는지
└── eval_history.jsonl 성능 측정 이력 (docs/04 참고)
```

지우고 처음부터 하고 싶으면 `review_data/` 폴더를 통째로 지우면 됩니다 (분석 기능에는 영향 없음).
이 폴더는 GitHub 저장소에는 올라가지 않습니다 (.gitignore 등록).

**`examples.broken-…json` 같은 파일이 보이면** — 저장 중에 프로그램이 꺼지는 등으로
`examples.json`(또는 `extra_rules.json`)이 읽을 수 없게 됐다는 뜻입니다. 도구는 그 파일을
지우지 않고 이름만 바꿔 옆에 두고 새로 시작하며, 그 사실을 [성능 기록] 탭의 **개선 타임라인**에
`예시 파일이 손상되어 …로 옮겨 두고 새로 시작했습니다` 한 줄로 남깁니다.
(쌓인 예시 수가 갑자기 줄었다면 이 줄이 있는지 확인하세요 — 원인이 여기 적힙니다.)

**손으로 고치려 하지 마세요.** 이 파일은 한 항목이 여러 줄에 걸친 형식이라 "잘린 줄만 지우기" 로는
복구되지 않고, 메모장으로 다시 저장하면 글자 코드가 바뀌어 오히려 한 번 더 깨집니다.
`.broken-…` 파일은 **그대로 두고**(원본 보존용), 검토완료본을 다시 올려 [반영 저장] 하면
예시가 새로 쌓입니다. 교정 기록 원본(`dataset.jsonl`)은 따로 있어서 없어지지 않습니다.

회사 보고에 쓰는 방법까지 [docs/04_성능_측정.md](04_성능_측정.md) 에 있습니다.
