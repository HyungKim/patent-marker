# 개선 이력 — 무엇을, 왜, 어떻게 바꿨고 얼마나 좋아졌나

이 문서는 **보고자료의 원천**입니다. 도구를 바꿀 때마다 아래 네 칸을 채운 항목을 하나씩 추가합니다.

| 칸 | 적는 것 |
|---|---|
| 개선 방법 | 무엇을 어떻게 했나 (한 줄) |
| 개선된 부분 | 어느 파일·화면·절차가 바뀌었나 |
| 개선 이유 | 어떤 문제·요구 때문에 했나 |
| 개선 결과 (정량) | 전후 숫자. **측정**한 값과 **추정**한 값을 구분해 적는다 |

날짜는 한국 시간 기준. 버전은 화면 제목 옆에 찍히는 `config.VERSION` 값이고, 저장소에 올릴 때마다 올립니다.
수치가 "측정" 이면 어디서 쟀는지(예시 문서 5장 / 회사 PC 실행 기록) 를 함께 적었습니다.

> 검토 반영으로 **판정 정확도**가 어떻게 변했는지는 이 문서가 아니라 화면의 [성능 기록] 탭이 회차마다 자동 기록합니다
> (재현율·정밀도·F1·등급일치, 최초 설정 대비 Δ). 보고 때는 그 탭의 [보고용 표 복사] 로 표를 가져오세요 (`docs/04_성능_측정.md`).
> 이 문서는 **프로그램 자체의 개선**(속도·안정성·사용성·산출물)을 다룹니다.

## 회차별 상세

### 1. 도구 완성과 공개 (2026-08-16 착수 → 08-24 GitHub 공개) — 버전 없음

- **개선 방법**: PPTX 보고자료에서 특허 출원 후보 구간을 찾아 형광펜으로 표시하는 도구를 만듦.
  읽기(extract) → 규칙 사전(lexicon) → 온디바이스 모델 판정(analyze, Ollama+Qwen3) → 병합(merge) → 마킹(mark) 5단계.
- **개선된 부분**: `app/` 전체, 웹 화면, 설치·실행 스크립트(Windows/Mac), 안내 문서 3편, 예시 문서·결과.
- **개선 이유**: 보고자료는 결과 위주라 발명이 문장에 빠져 있는 경우가 대부분 → "수단이 존재함을 시사하는 표현"까지 잡아
  변리사에게 넘길 후보를 빠짐없이 추리기 위해. 인터넷 없이, 문서가 PC 밖으로 나가지 않는 조건.
- **개선 결과**: 규칙 30여 개·카테고리 11종·등급 A/B/C. 통신은 127.0.0.1(같은 PC 의 Ollama)만. 외부 요청 0건.

### 2. 기본 모델 qwen3:14b → qwen3:8b (2026-09-18)

- **개선 방법**: 기본 모델을 8b 로 낮추고 14b 실행 파일(`run_14b.bat`)을 없앰. 업그레이드는 `PM_MODEL` 환경 변수로.
- **개선된 부분**: `app/config.py` MODEL, 루트 스크립트, README, 안내 문서, 점검 스크립트.
- **개선 이유**: 회사 PC 에 GPU 가 없고 RAM 16GB 로 확정. 14b(9.3GB)는 메모리에 겨우 올라가고 CPU 에서 너무 느림.
- **개선 결과**: 모델 파일 9.3GB → 5.2GB(−44%). CPU 에서 토큰당 속도는 메모리 읽기량에 반비례하므로 **약 1.8배 빠름(추정, 이론치)**.
  실측은 회사 PC `review_data\run_log.tsv` 의 "쓰기토큰/초" 로 확인.

### 3. 검토 반영 + 성능 측정 (2026-09-19)

- **개선 방법**: 사람이 형광펜을 교정한 **검토완료본**을 올리면 도구의 판정과 비교해 오탐(빼야 할 것)·누락(넣어야 할 것)을 추출,
  **규칙 사전과 프롬프트 예시에 자동 반영**. 그리고 확정된 정답을 문제지 삼아 **최초 설정 vs 현재 설정을 같은 문제로 A/B 채점**.
- **개선된 부분**: `app/review.py`(신설), `app/evaluate.py`(신설), 화면 [검토 반영]·[성능 기록] 탭, `docs/03`, `docs/04`, 점검 스크립트.
- **개선 이유**: 도구가 쓸수록 좋아져야 하고, "얼마나 좋아졌는지" 를 회사에 숫자로 보고해야 함. GPU 가 없어 파인튜닝은 불가 →
  데이터(교정 내역)를 쌓아 사전·프롬프트로 반영하는 길을 택함.
- **개선 결과**: 검토완료본 1개 → 교정 내역 자동 추출·반영 (수작업 0). 지표 4종(재현율·정밀도·F1·등급일치) + 최초 대비 Δ 자동 산출,
  회차마다 `review_data/eval_history.jsonl` 누적. **실제 수치는 회사 PC [성능 기록] 탭에 쌓임** — 보고 때 [보고용 표 복사].
  (해석 원칙: 문제지가 회차마다 자라므로 회차 간 절대값보다 **같은 회차 안의 최초→현재 Δ** 를 개선 폭으로 읽는다.)

### 4. 14b 경로 정리, 오프라인 꾸러미 축소 (2026-09-19)

- **개선 방법**: GPU 확보 불가 확정에 따라 저장소·문서·꾸러미 스크립트에서 14b/고품질 경로를 정리.
- **개선된 부분**: `tools/` 꾸러미 스크립트, 문서, README.
- **개선 이유**: 두 갈래 안내가 초보 사용자를 헷갈리게 하고, 꾸러미가 USB 용량을 넘김.
- **개선 결과**: 오프라인 꾸러미 15GB → 약 6GB(−60%).

### 5. 검토완료본 복수 업로드 (2026-09-19)

- **개선 방법**: 여러 검토완료본을 한 번에 올려 파일별로 독립 처리. 깨진 파일은 그 파일만 제외, 같은 문서 두 벌은 첫 벌만.
- **개선된 부분**: `review.preview_many()`, 화면 [검토 반영] 탭, 점검 6건.
- **개선 이유**: 검토는 한 번에 여러 문서가 돌아오는데 하나씩 올리는 게 번거로움.
- **개선 결과**: 업로드 N회 → 1회. 오류 파일이 나머지 파일의 반영을 막지 않음.

### 6. 변경 일지·개선 타임라인 (2026-09-19)

- **개선 방법**: [반영 저장] 때 데이터·주입 예시·사전 개수의 **전후**를 `review_data/change_log.jsonl` 에 기록하고,
  [성능 기록] 탭에 성능 측정 결과와 시간순으로 병합해 보여 줌. [보고용 표 복사]에 포함.
- **개선된 부분**: `review.commit_with_log()`, 화면 타임라인, `docs/03`·`04`.
- **개선 이유**: "무엇을 바꿨더니(입력) → 얼마나 좋아졌나(측정)" 가 한 시간축에 있어야 보고 서사가 됨.
- **개선 결과**: 반영 1회마다 전후 기록 자동(수동 기록 0). 최근 40행 표시.

### 7. 표시 방식 — 구간마다 문구 대신 첫 슬라이드 범례 (2026-09-19)

- **개선 방법**: 표현을 "특허검토필요" → **"출원검토필요"** 로, 구간마다 붙이던 【문구】 대신 첫 슬라이드에 색상 범례 상자 하나.
  문구는 흑백 인쇄용 선택 옵션으로만(기본 해제). 예전 문구가 든 파일도 검토 반영이 알아봄(`LEGACY_*`).
- **개선된 부분**: `app/mark.py`, `config.py`, `review.py`, 화면 옵션, 문서, 예시 결과.
- **개선 이유**: 구간마다 문구가 붙으면 슬라이드 레이아웃이 깨지고 읽기 어려움.

  - **bge-m3 는 이 시험에서 이득이 없었다**(같은 재현율, 정밀도 −2.6p). 시험 문서가 재사용 장표 위주라 "단어가 다른 새 문장" 이 거의 없어
    뜻 기준 검색이 힘을 쓸 자리가 없었음 — 회사 문서가 쌓인 뒤 [성능 기록]으로 재평가. 기본은 켜 두되 PC 가 버거우면 끄면 됨.
  - **내장 성능 측정(같은 문단, leave-one-out)**: 최초 70.6 / 100 / 82.8 → 현재 73.5 / 92.3 / 81.9 (재현율 +2.9p, 정밀도 −7.7p).
    같은 문단끼리는 자기 기억을 빼고 재므로 이득이 작고, 사례 주입이 모델을 조금 더 잡게 만들어 정밀도가 내려감 — 검토가 여러 문서로
    쌓일수록 이 수치가 올라가는지가 다음 회차의 관찰 대상.
  - 소요 시간은 학습 켬에서 +14~32%(사례 프롬프트가 슬라이드마다 붙고 모델이 후보를 더 씀). 회사 PC 에서는 슬라이드당 +5~10초 추정.
- **자원 (회사 PC 16GB 기준)**: 기억 색인은 검토 수천 건이어도 수 MB(RAM). bge-m3 만 별도 — 다운로드 1.2GB, 로드 시 RAM 약 1.2GB, 문서당 임베딩 10~30초(추정).
  `dataset.jsonl` 본문 전체 저장은 줄당 최대 수백 바이트 증가로 무시할 수준이며 프롬프트에는 들어가지 않음.

### 18. PDF 입력 — 파워포인트를 PDF 로 변환한 보고서도 그대로 (2026-09-28) — 버전 2026-09-28b (19회차와 같은 업로드)

- **개선 방법**: `.pdf` 를 PPTX 와 같은 파이프라인에 태우는 `app/pdfdoc.py` 신설.
  ① 읽기 — pdfminer.six 로 글상자(TextBox)마다 글자를 꺼내 문단(`Segment`)으로 만들고, 글자 하나하나의 쪽 위 좌표를 함께 저장.
  한글 줄바꿈은 공백 없이 잇고 영문·숫자 줄바꿈은 공백 하나로 이어, PPTX 문단과 같은 글자열이 되게 함.
  ② 마킹 — 칠할 구간의 글자 좌표를 줄 단위 네모로 묶어 **형광펜 주석**(Highlight annotation)으로 넣음. 색은 PPTX 와 같은 A/B/C 색,
  주석 메모에 "[등급] 라벨 · 분류 · 사유", 1쪽에 범례 메모(스티커)와 A/B/C 색 견본. 결과는 `이름_특허마킹.pdf`.
  주석마다 **모양 스트림(/AP)** 을 직접 넣음 — Acrobat·Edge·Chrome 은 없어도 그려 주지만, 탐색기 미리보기·macOS 훑어보기·일부 구형 뷰어는 /AP 가 없으면
  형광펜을 아예 안 보여 준다(확인: 훑어보기 렌더링에서 /AP 없을 때 0개 → 넣은 뒤 전부 표시). 곱하기 혼합으로 칠해 글자가 가려지지 않음.
  ③ 검토본 읽기 — 뷰어에서 고친 형광펜 주석의 네모 안에 글자 중심이 드는 글자들을 구간으로 되살려 기존 `review.diff` 에 그대로 넘김
  (지우면 오탐, 새로 칠하면 누락, 색을 바꾸면 등급 변경). 검토 학습 ①②③·성능 측정도 문단 글자열 기준이라 그대로 적용.
  형식 판별은 확장자(`.pdf`)이며 `extract.extract` / `review.read_reviewed` 가 분기. 문구 삽입 옵션(【출원검토필요】)은 PDF 에서 무시(글자를 고칠 수 없는 형식).
- **개선된 부분**: `app/pdfdoc.py`(신설), `extract.py`·`review.py`(`.pdf` 분기), `pipeline.py`(PDF 저장 분기·"PDF 마킹 중" 단계), `local.py`(허용 확장자·결과 이름 `.pdf`),

### 19. 형광펜 기본색 — 회사 장표에서도 한눈에 띄는 선명한 색으로 (2026-09-28) — 버전 2026-09-28b

- **개선 방법**: `config.GRADE_COLOR` 기본값을 연한 파스텔(앰버 FFD54F · 하늘 9FD8F5 · 살구 FF9E80)에서 PowerPoint 형광펜 기본색과 같은
  **노랑 FFFF00 · 청록 00FFFF · 빨강 FF5050** 으로 교체. 세 색은 색상각이 60°·180°·0° 로 서로 가장 멀고 밝기도 층이 져(흑백 인쇄·색각 이상에서도 구분)
  검은 글자가 그대로 읽힌다. 검토 반영의 색 → 등급 판정(`review.color_to_grade`)은 기준 색상각을 등급마다 여럿 두는 구조(`_HUE_ANCHORS`)로 바꿔
  새 색·예전 색·PowerPoint 형광펜 기본색(노랑·청록·파랑·빨강·분홍)을 모두 같은 계열로 알아본다 → 예전 색으로 마킹한 검토본도 그대로 반영된다.
- **개선된 부분**: `config.py`(GRADE_COLOR·주석), `review.py`(`_HUE_ANCHORS`), `pdfdoc.py`(범례 문구·기본색), 화면·README·`docs/01`·`docs/03`(색 계열 표),
  `samples/회사보고자료_예시_마킹결과.pptx`(같은 판정, 새 색으로 다시 칠함). 색만 바꾸고 싶으면 여전히 `config.GRADE_COLOR` 세 값만 고치면 된다.
- **개선 이유**: 사용자 보고 "마킹된 형광펜 색이 회사 PPT 에서는 찾기 힘들다". 회사 장표는 색 상자·옅은 배경·작은 글자가 많아 파스텔 형광펜이 배경에 묻혔다.
- **개선 결과 (계산값 — 색 수치로 계산한 것이고, 체감은 회사 장표에서 확인):**

  | | A | B | C |
  |---|---|---|---|
  | 색 | FFD54F → **FFFF00** | 9FD8F5 → **00FFFF** | FF9E80 → **FF5050** |
  | 색 진하기 (HSV 채도, 1 = 가장 진함) | 0.69 → **1.00** | 0.35 → **1.00** | 0.50 → **0.69** |
  | 검은 글자 대비 (WCAG, 본문 기준 4.5 이상) | 14.9 → 19.6 | 13.6 → 16.7 | 10.5 → 6.5 |
  | 세 색 사이 색상각 간격 | 46°·203°·14° (A–C 32°) | → | 60°·180°·0° (최소 60°) |

  - 옅은 파랑 상자(예: DEEBF7) 위에서 예전 하늘색(9FD8F5)은 배경과 거의 같은 색이었으나 청록(00FFFF)은 진하기 차이로 바로 구분된다.
  - **실제 체감은 회사 장표에서 확인** — 여전히 찾기 힘들면 `config.GRADE_COLOR` 만 바꾸면 되고, PowerPoint 2013 이하처럼 형광펜을 아예 안 그리는 환경이면
    "형광펜 뒤에 【출원검토필요】 문구도 표시" 옵션을 켜서 만든다.
- **바꾸지 않은 것**: 등급 뜻·색 계열 규약(노랑 = A, 청록·파랑 = B, 빨강·분홍 = C), 밑줄·글자색 처리(어두운 배경이면 글자를 어둡게 유지).

### 20. 원본 형광펜 지우고 시작 — 작성자의 강조가 도구 표시·검토 학습에 섞이지 않게 (2026-09-29) — 버전 2026-09-29 (저장소에는 21회차와 함께 2026-09-30 으로 올라감)

- **개선 방법**: 분석을 시작할 때 원본에 있던 형광펜을 걷어내는 `app/prehl.py` 신설. 걷어내는 것은 메모리에 올린 사본(= 저장되는 마킹본)에서만이고
  원본 파일은 바뀌지 않는다. 그 결과 마킹본의 형광펜은 전부 "도구가 칠한 것 + 검토자가 고친 것" 이 되어, 검토 반영의 읽기 규칙을 바꾸지 않고도 섞이지 않는다.
  ① **PPTX** — 글자(런)의 `<a:highlight>` 를 제거. 형광펜에 맞춰 고른 글자색 때문에 글자가 안 보이게 되는 경우(진한 형광펜 + 흰 글자 등)는 글자색을 보정.
  ② **PDF 주석** — 뷰어로 칠한 형광펜 주석을 삭제 (메모·링크 등 다른 주석은 그대로).
  ③ **PDF 에 굳은 형광펜** — 파워포인트가 PDF 로 저장할 때 형광펜은 주석이 아니라 색 네모 그림이 된다. 글줄에 딱 붙은 밝고 선명한 채움 네모를 찾아
  그 위에 채도 혼합 → 닷지 혼합 → 색 혼합을 덧그려 바탕색으로 만든다. 덮는 세기를 형광펜 밝기에 맞춰 글자가 가늘어지지 않게 했다.
  표 칸·도형 채우기(글자보다 넓음), 밝은 글자, 어두운 바탕은 건드리지 않고 "그대로 둠" 으로 센다.
  ④ **도구가 예전에 넣은 표시**(밑줄 서명이 있는 형광펜·범례 상자·문구)를 알아보고 걷어내, 마킹본을 다시 분석해도 범례가 겹치지 않는다.
  ⑤ **켜고 끄기** — 화면 "원본 형광펜 지우고 시작"(기본 켬), 명령행 `--keep-highlights`, `PM_STRIP_HL`, 굳은 형광펜 덮기만 끄는 `PM_PDF_COVER`.
  끄면 결과에 "N곳을 그대로 두었습니다 — 검토 반영 때 검토자가 칠한 것으로 읽힐 수 있습니다" 경고가 나온다.
  부수 수정: pdfminer 가 그림 상태를 저장할 때 색 공간을 빠뜨려 색을 잘못 읽는 문제를 `pdfdoc._Interpreter` 로 보정(노랑 `1 1 0` 이 `0` 으로 읽히던 것).
- **개선된 부분**: `app/prehl.py`(신설), `extract.py`(`strip_highlights`), `pdfdoc.py`(해석기 보정·굳은 형광펜 찾기·저장 시 정리), `pipeline.py`(결과 한 줄·실행 기록 "원본형광펜" 칸),
